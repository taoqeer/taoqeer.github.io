How I made a tax processing script 240× faster

May 2025 · 7 min read

At EY, I inherited a Python script that generated GST compliance reports — GSTR-3B reconciliation, tax liability summaries, the kind of thing that finance teams needed before every filing deadline. It worked. The problem: it took over 2 hours to run. Every. Single. Time.

By the time I was done, it ran in under 30 seconds. That's a 240× improvement. This is the story of how I got there — not just the fixes, but how I thought about the problem.

The situation

The script processed large DataFrames of invoice records, matched them against tax rate tables, applied GST computation logic, and produced reconciled reports. It had been written quickly, worked well enough on smaller datasets, and then just... kept running on production data that had grown 10× over two years.

Nobody had touched the performance because it technically worked. But two hours per run meant finance teams couldn't iterate — if something looked wrong in a report, re-running to verify a fix meant waiting another two hours. It was becoming a blocker.

Step 1: Don't guess. Profile first.

The worst thing you can do when optimizing is start changing code without data. Intuition is usually wrong. I ran Python's built-in cProfile to get a real picture of where time was actually going. 

import cProfile
import pstats

profiler = cProfile.Profile()
profiler.enable()

run_gst_report()  # the slow function

profiler.disable()
stats = pstats.Stats(profiler)
stats.sort_stats('cumulative')
stats.print_stats(20)

The output was eye-opening. Three bottlenecks showed up immediately:

  1. Excessive memory usage from large DataFrames being loaded and reloaded
  2. Inefficient indexing — iloc[] used everywhere for lookups
  3. Python for-loops over DataFrames doing row-by-row computation

I hadn't written any of this. But the profiler made the problem undeniable, which is what I needed to justify the time spent fixing it.

Step 2: Fix the indexing — .at[] instead of .iloc[]

The script used .iloc[] for most cell lookups and merge operations. .iloc[] is position-based and does bounds checking on every access. For a script doing millions of lookups, this adds up fast.

Switching to .at[] for scalar lookups (label-based, no bounds overhead) and .loc[] for row/column access gave an immediate speedup on the merge and vlookup-heavy sections of the script. 

# Before — positional lookup, slower
value = df.iloc[row_index, col_index]

# After — label-based scalar access, faster
value = df.at[row_label, col_name]

This sounds minor. In tight loops over 200k+ rows, it's not.

Step 3: Vectorize — kill the for-loops

The computation logic was doing row-by-row iteration in Python. This is one of the most common Pandas anti-patterns — Python loops are slow, and Pandas is built for vectorized column operations. 

# Before — row-by-row Python loop
results = []
for idx, row in df.iterrows():
    results.append(compute_gst(row['amount'], row['category'], row['state']))
df['gst'] = results

# After — vectorized with apply
df['gst'] = df.apply(
    lambda row: compute_gst(row['amount'], row['category'], row['state']),
    axis=1
)

# Even faster — NumPy where for binary conditions
df['gst'] = np.where(
    df['category'] == 'goods',
    df['amount'] * 0.18,
    df['amount'] * 0.05
)

For the GST rate logic (which had several category branches), np.where and np.select handled conditions that previously needed nested if-statements inside a loop.

Step 4: Stop reloading large DataFrames from CSV

The script loaded the same reference tables — GSTIN master data, HSN code mappings, state tax rates — from CSV on every run. These files were large. Parsing CSV is slow.

I cached them as pickle files. Pickle deserializes a DataFrame roughly 10–50× faster than parsing CSV, because it stores the binary representation directly. 

import pickle
from pathlib import Path

def load_reference_data(csv_path):
    pkl_path = Path(csv_path).with_suffix('.pkl')
    if pkl_path.exists():
        with open(pkl_path, 'rb') as f:
            return pickle.load(f)
    df = pd.read_csv(csv_path)
    with open(pkl_path, 'wb') as f:
        pickle.dump(df, f)
    return df

First run still parses CSV and writes the pickle. Every subsequent run uses the cache. Reference data that changed infrequently (HSN codes, state rates) got a significant speedup from this alone.

How I shipped it

I didn't rewrite the whole script at once. That would have been risky — this was live, client-facing code. Instead I raised small, reviewable PRs for each optimization in isolation: indexing fix first, then the vectorization pass, then the pickle caching. Each PR was independently testable and didn't change business logic — only the execution path.

The stakeholding developers could review each change, run their own validation against known-good output, and merge with confidence. No big-bang rewrite, no regression risk, no "trust me it's faster" hand-waving.

Result

Across all three optimizations — indexing, vectorization, pickle caching — the script went from 2+ hours to under 30 seconds. A 240× improvement. Data integrity was maintained throughout; the output was byte-for-byte identical to the previous version on test datasets.

The client noticed. The finance team went from dreading re-runs to actually iterating on reports. My team lead flagged it to senior leadership, and I ended up winning the EY Exceptional Award for the quarter.

The lesson

The fixes themselves weren't clever. .at[] over .iloc[], vectorization, pickle caching — none of this is advanced. What made the difference was profiling before touching anything. Without the profiler, I would have guessed wrong about where the time was going and spent a week optimizing the wrong thing.

Measure first. Then fix exactly what's slow.
